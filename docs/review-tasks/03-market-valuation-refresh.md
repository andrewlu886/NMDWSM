# 任務 3 建立行情更新與估價資料銜接

對應覆核表第 3 點。優先度 P0：不得把套用靜態參考價的結果宣稱為隨市場即時修正。

## 最優先缺陷

現有估價能自動計算，但參考價格更新與估價輸入沒有完整的市場資料選擇契約。只新增定時爬蟲，未明確決定哪筆價格可作估價基準，仍可能以舊資料或錯誤商品價格產生看似精確的結果。

## 現況證據

- `public/server.js` 的 `/api/valuation` 已驗證輸入、查詢 `HardwareCatalog.resolveValuationInput()` 並呼叫既有公式，不是完全人工估價。
- `public/db.js` 的 `findCpuPricingModel()`、`findReferencePrice()` 讀取 CPU 定價表與匯入參考價。這些不是持續更新的成交行情資料流。
- `src/services/market-cache.js` 是查詢觸發的快取更新，TTL 與 `nextUpdateAt` 不等於背景排程已執行。
- `public/server.js` 有匯率更新計時器；目前未見新品與二手行情的持久化更新工作系統。不能把匯率排程視為已完成市場報價排程。
- `src/services/valuation.js` 已有多類公式與版本資訊，應沿用而非由聊天模型另外算價。

## 修改範圍

1. 在任務 1、2 的資料契約上建立排程工作：限定型號集合、批次大小、來源速率、互斥鎖、重試與工作狀態；重新啟動後可恢復，不能重複啟動多份爬取。
2. 明確定義可用價格優先序與限制：完整型號、幣別、單件／組合價、品況、來源時間、樣本數與異常值。二手刊登價不能當新品基準價，成交價須有核實標記。
3. 建立單一價格選擇服務，供既有估價 API 使用；回傳來源 ID、觀測時間、選用原因、降級原因與公式版本。不同類別公式的「原價／新品參考價」語義先確認，不能一律替換成最新刊登價。
4. 新資料取得失敗時保留前次成功值，明確標示過期；超過可接受期限時要求補資料或停止估算，不把失敗記成零元或成功更新。
5. 用有證據的成交案例建立離線誤差評估，先報告樣本量及涵蓋範圍；參數調整需版本化、審核及可回退，不讓排程自動改公式。

## 驗收條件

- 固定快照輸入與相同條件得到相同估價；回應可追溯實際採用的價格與公式版本。
- 測試來源失敗、過期資料、僅有組合價、不同尾碼、零樣本與極端價格；不得替換相近 SKU。
- 排程重啟、重試與並行時不重複寫入，不覆蓋前次成功觀測時間。
- 關閉本機網站後更新會停止的部署限制須在文件明示；需要全天候更新時才部署常駐服務，不能依賴使用者開著頁面。
- 保留 `/api/valuation` 現有計算契約與回歸測試；先完成資料銜接，再另行評估公式修正。

## 依賴

依賴任務 1 的快照儲存及任務 2 的價格種類契約；提供任務 4 判斷降價的可信資料來源。
