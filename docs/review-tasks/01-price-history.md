# 任務 1 建立可追溯的歷史價格與折舊圖表

對應覆核表第 1 點。優先度 P1；歷史資料契約是任務 3、4 的前置依賴。

## 最優先缺陷

目前沒有可直接用來繪製市場歷史曲線的完整時序資料。若將最新快取或使用者查詢紀錄畫成歷史行情，會混淆查詢時間、實際報價及推估價格。這是資料基礎缺口，不是單純缺少 Chart.js。

## 現況證據

- `src/services/market-cache.js` 的 `createMarketCache().get()` 依關鍵字及平台儲存目前結果；更新時 `entries.set(key, entry)` 覆寫前一筆，最多保留 500 個查詢鍵，並非保留每個商品每一天的價格。
- `public/history-store.js` 使用瀏覽器 IndexedDB，`MAX_RECORDS = 20`，用途是本機查詢／估價歷史，不能代表完整市場時間序列。
- `public/db.js` 及現行 SQLite 結構有參考價格與型號資料，未見商品報價快照專用表。

## 修改範圍

1. 新增報價快照表及資料遷移。最少保存完整型號 ID、平台、商品／刊登 ID、來源網址、價格、幣別、商品狀況、價格種類、觀測時間、刊登時間（可空）、來源狀態與批次 ID。
2. 價格種類採任務 2 的共同契約：新品刊登、二手刊登、核實成交與公式估算不能混在同一價格欄位語義中。
3. 快照追加寫入並有批次去重鍵，保留價格改變的時間；同一次重試不能灌入重複點。若聚合成每日曲線，明列中位數等算法、來源及樣本數。
4. 加入依完整 SKU、時間範圍及價格種類查詢的 API，限制查詢範圍與回傳筆數。
5. 接入 Chart.js。實際報價與公式曲線分開標示；公式曲線保存公式版本、基準價及使用條件，名稱使用「推估折舊」，不得稱為歷史成交價。
6. 無資料、斷日、來源失敗時顯示缺資料，不插值成實際觀測、不補零元，也不回填不存在的歷史。

## 驗收條件

- 同商品在不同日期有不同報價時，重啟後仍保留兩筆；同批次重試不重複。
- i7-14700 與 i7-14700K，以及 GPU 不同容量／WHITE 等變體分開查詢。
- 新品、二手刊登、核實成交、公式推估可以清楚分辨；工具提示含來源與時間。
- 空資料、單一資料點、來源中斷、不同幣別及異常價格都有測試。
- 未提供核實成交樣本時，不顯示「成交趨勢」。有觀測紀錄不等同足以預測最佳購買時機。

## 不在本任務內

不重寫估價公式、不自動推導成交價、不承諾準確預測漲跌。排程與價格選擇由任務 3 負責。
