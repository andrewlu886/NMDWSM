# 任務 4 建立降價提醒與訂閱安全

對應覆核表第 4 點。功能優先度 P2；訂閱資料隔離與端點驗證是公開上線前的 P0 門檻。

## 最優先缺陷

目前尚未建立完整訂閱與發送流程。新增推播時，如果只保存 endpoint 並提供刪除 API，卻沒有證明訂閱歸屬，可能讓別人讀取、修改或刪除他人的追蹤資料。這是新功能必須防止的風險，不是已證實目前網站存在的推播漏洞。

## 現況證據

- 現行 `public/server.js` 路由與 `public/db.js`／SQLite 結構未見推播訂閱、價格追蹤及通知發送紀錄。
- 現行前端及套件設定未見已接妥的 Web Push、Service Worker 訂閱與發送流程。
- `public/server.js` 明確停用舊登入／帳號路由，因此不能假定舊 users 資料表代表目前已具備可用的登入授權機制。
- `scripts/launch-website.js` 的本機啟動方式會隨關閉而停止服務；後端停機時不會繼續比較價格。

## 修改範圍

1. 先選定訂閱歸屬方案：可使用經驗證帳號，或不可猜測且由伺服器驗證的裝置／訂閱管理憑證。所有查詢、修改與取消都核對歸屬，不能只靠前端傳來的 ID。
2. 由使用者主動按下訂閱後才請求瀏覽器通知權限；拒絕或不支援時給出可理解的狀態。
3. 保存訂閱、完整商品條件、目標價格、價格種類、建立時間與最後通知時間。endpoint 與金鑰不得出現在公開 API、聊天紀錄或一般日誌。
4. 驗證推播 endpoint 的格式與允許目的地，使用標準發送套件；不能讓任意輸入變成後端對內網地址的請求。VAPID 私鑰只在後端環境配置。
5. 從任務 3 的有效報價觸發提醒，明確排除過期、幣別不符、組合價、已售出與錯誤型號。
6. 設計去重與冷卻期：同一次符合條件不連續轟炸；發送失敗有有限重試，失效訂閱停用。取消後移除訂閱及待發送工作。
7. 定義部署方式與 HTTPS；本機關閉即停止追蹤必須告知，若需求是全天候提醒需另有常駐後端。

## 驗收條件

- A 使用者／裝置不能讀取、改動或取消 B 的訂閱；無憑證與錯誤憑證皆拒絕。
- 通知權限拒絕、失效 endpoint、重複事件、並行工作、取消與發送競爭都有測試。
- 測試私有網段、回環地址、非 HTTPS 與不受信任端點，確認發送介面不能被當作任意請求代理。
- 私鑰不出現在前端 bundle；日誌不輸出完整訂閱資訊。
- 只有指定型號的有效價格符合門檻才提醒；重新啟動後不重發同一事件。

## 範圍限制

此文件定義安全驗收需求，不代表已完成安全稽核或授權擴大部署。依賴任務 1、3 的商品快照與更新機制。
